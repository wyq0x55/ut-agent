# 嵌入式单元测试（WinAMS）自动化方案

> 项目制交付场景：新代码 → C++ Extractor 提取 Typed FunctionIR → 确定性规则引擎生成 (Obligation → Constraint → Solve → Evaluate → Oracle → Validate → Suite) → WinAMS 目标投影 (TestCsv / Harness / DefineVar / Stub) → WinAMS 执行 → 测试报告 → 审查说明与 Gap 闭环

---

## 1. 总体架构与职责划分

| 环节 | 性质 | 实现方式 |
|---|---|---|
| C 源码语义提取 | 确定性 | `tooling/ut-clang-extract` (C++ LibTooling) 唯一 C 源码事实源，输出 Typed FunctionIR (v3) |
| 组合式策略定义 | 确定性 | `ResolvedTestPolicy = Base TestBaseline + Requirement Modules (MC-DC) + ProjectRulePack` |
| 规则引擎与用例生成 | 确定性 | 8 阶段确定性生成引擎 (`generation/`: Obligation → Constraint → Solve → Evaluate → Oracle) |
| 预期效果 (Oracle) 计算 | 确定性 | `SemanticEvaluator` 根据 UUT 源码语义计算 post-state，提取 Caller-visible expected effects |
| WinAMS 目标投影 | 确定性 | `targets/winams/`: CP932/CRLF TestCsv, Harness, DefineVar 与 Stub 生成 |
| 报告与证据链 | 确定性 | `reporting/`: 差异报告与证据链渲染 |
| 有状态 stub / 复合逻辑 | 智能介入 | LLM 生成带计数/分支的 stub 行为代码 |
| 覆盖率闭环补用例 | 智能介入 | LLM + 覆盖率反馈循环 |
| 审查说明起草 | 智能介入 | LLM 结合源码起草审查说明，人工审核 |

**核心原则：约 90% 以上的用例由纯确定性引擎生成，LLM 仅在三个环节介入（来源判定兜底、有状态 stub、审查说明 + 覆盖率闭环）。Token 花在刀刃上，确定性生成永无随机幻觉。**

---

## 2. 确定性测试生成主链路

正常生成（`ut-agent gen`）严格遵守确定性生成主链路：

```
                C Source + CompileContext
                            │
                            ▼
           ut-clang-extract (C++ LibTooling)
                            │
                            ▼
          Typed FunctionIR v3 (JSON / Dataclass)
                            │
                            ▼
    ResolvedTestPolicy (Base Baseline + Requirements + ProjectRules)
                            │
                            ▼
┌─────────────────────────────────────────────────────────┐
│              确定性测试生成引擎 (generation/)             │
├─────────────────────────────────────────────────────────┤
│ 1. Obligation  │ 根据策略与 IR 构造测试观点 (C0/C1/MC-DC)   │
│ 2. Constraint  │ 将观点转换为类型化域约束                   │
│ 3. Solve       │ 确定性求解输入组合与 Witness                │
│ 4. Evaluate    │ 基于 C 源码语义计算 post-state (Evaluator)  │
│ 5. Oracle      │ 提取 Caller-visible 期望效果 (Expected Effects) │
│ 6. Validate    │ 校验输入合法性与 Oracle 完整性               │
│ 7. Suite       │ 组合、去重与排序测试用例                     │
└─────────────────────────────────────────────────────────┘
                            │
                            ▼
                 WinAMS Projection (targets/winams/)
                            │
                            ▼
              TestCsv / Harness / DefineVar / Stub
```

**铁律**：正常生成（`ut-agent gen`）**绝对禁止**读取历史 Golden TestCsv 或外部预期结果补算 Oracle。所有 Expected Effects 必须通过 UUT 源码语义求值得到。

---

## 3. WinAMS 函数隔离模式下的输入模型

WinAMS 将每个函数隔离、独立运行测试，被测函数的可控环境输入只有三类：

1. **函数入参**
2. **全局变量前置状态**
3. **stub 函数的返回值与指针输出**（按测试用例逐个设置）

WinAMS 目标适配层将 `SemanticTestSuite` 准确物化映射到 WinAMS TestCsv / Harness / DefineVar 中。

---

## 4. 闭环与 Gap Taxonomy

语料库校验（`learning`）支持与历史 Golden TestCsv 的语义比对，所有差异必须按照统一 Gap 分类法（Gap Taxonomy）归类并在最上游根因层修复：

- `BASELINE_GAP` / `PROJECT_RULE_GAP` / `FUNCTION_IR_GAP`
- `OBLIGATION_GAP` / `SOLVER_GAP` / `EVALUATOR_GAP` / `ORACLE_GAP`
- `SUITE_GAP` / `HARNESS_GAP` / `PROJECTION_GAP` / `GOLDEN_ERROR`

修复原则：打补丁被严格禁止，所有修复必须在 root cause 层落地，并同步包含 synthetic 单元测试与真实函数回归测试。
