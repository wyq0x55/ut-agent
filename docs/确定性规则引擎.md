# 确定性测试规则引擎

规则引擎位于源码解析与 WinAMS 渲染之间：

```text
FunctionIR → TestObligation → Constraint → TestIntent → ValidationResult → TestCsv
```

正常生成只读取源码、配置和已审批规则包。人工 TestCsv 只允许通过
`rules infer` 离线归纳候选规则，不会在 `gen` 或 `project` 中隐式读取。

## 生成门禁

每条 `TestIntent` 必须证明参数和值域合法、目标分支结果正确，并为所有返回值、
可写指针、全局写回和寄存器写回提供 oracle。未满足这些条件的用例只写入
`test-intents.json`，状态为 `NEEDS_REVIEW` 或 `UNSUPPORTED`，不会以默认零值
写入 TestCsv。

通用求解器支持整数/枚举/布尔比较、`&&`、`||` 和整数位掩码。它在有限候选
集合上求值并为每个可达分支选择稳定的最小代表，不使用随机数或网络。

## 规则包

规则包为 UTF-8 JSON：

```json
{
  "name": "dma-reviewed",
  "version": 1,
  "rules": [
    {
      "id": "project.Dma_Error.scenarios",
      "status": "approved",
      "scope": {"function": "Dma_Error"},
      "match": {"kind": "scenario_matrix"},
      "action": {"input_columns": [], "output_columns": [], "scenarios": []},
      "priority": 10,
      "evidence": ["sha256:...", "review note"],
      "approval": {"authority": "reviewer", "reason": "人工用例语义确认"}
    }
  ]
}
```

`candidate`、`approved`、`rejected` 是合法状态。只有 `approved` 会在运行时参与
生成；已批准规则必须填写 `approval`。相同作用域、规则类型和优先级的冲突会
直接报错，不能依赖文件顺序决定结果。

## 工作流

先从人工用例生成候选规则：

```bash
ut-agent rules infer Dma.c -f Dma_Error \
  -I <include> --golden <TestCsv.csv> -o dma-rules.json
```

归纳同一模块的其他函数时加 `--merge`。工具会保存 golden 的 SHA-256、列角色、
场景和取值类别。审核者确认规则后，将状态改为 `approved` 并填写审批记录，再运行：

提交前可检查审批状态：

```bash
ut-agent rules check dma-rules.json --require-approved
```

批准时必须显式指定审批标识和依据；命令写出新文件，不覆盖候选包：

```bash
ut-agent rules approve dma-rules.json -o dma-rules-approved.json \
  --authority reviewer --reason "DMA golden 语义复核"
```

```bash
ut-agent gen Dma.c -f Dma_Error -I <include> \
  --rules dma-rules.json --out .build/Dma_Error

ut-agent project <Soft> --manifest <project.json> --rules dma-rules.json \
  --out <winams-output> --no-build
```

每个函数同时生成 `test-intents.json`，其中包含测试义务、约束、规则追踪、输入、
期望值和验证错误。`project --check-golden` 比较语义签名，不再要求 CSV 字节一致。
