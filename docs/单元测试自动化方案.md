# 嵌入式单元测试（WinAMS）自动化方案

> 项目制交付场景：新代码 → 抽取被测函数 → 生成 stub → 编译 ELF → C0/C1/MC/DC 覆盖率测试 → 边界值用例 → WinAMS 执行 → 测试报告 → 审查说明

---

## 1. 总体结论

| 环节 | 性质 | 方案 |
|---|---|---|
| 抽取被测函数 | 确定性 | libclang 解析调用关系，脚本自动识别内部/外部函数 |
| 生成 stub 骨架 | 确定性 | 脚本生成；WinAMS 本身也带 stub 自动生成功能 |
| 编译 ELF | 确定性 | 脚本调用编译器 + WinAMS 工程 |
| 边界值枚举（±1 / min / max / 本身） | 确定性 | 输入域明确后为排列组合，脚本枚举 |
| C0/C1/MC/DC 用例组合 | 确定性 | 语法树拆原子条件 + 标准组合算法 |
| 跑 WinAMS | 确定性 | WinAMS 命令行批处理（CSV 驱动测试数据） |
| 生成报告 | 确定性 | 模板 + 解析 WinAMS 输出 |
| 条件变量 → 测试输入映射（复杂情况） | 需要智能 | LLM 兜底（数据流分析失败时） |
| 有状态 stub（依赖调用次数/顺序） | 需要智能 | LLM 生成带计数/分支的 stub 行为 |
| 覆盖率闭环补用例 | 需要智能 | LLM + 覆盖率反馈循环 |
| 审查报告起草（未达标原因说明） | 需要智能 | LLM 结合源码起草，人工审核 |

**核心原则：约 90% 的用例由纯脚本生成，LLM 只在三个环节介入（映射兜底、有状态 stub、审查说明 + 覆盖率闭环）。Token 花在刀刃上，能枚举的部分永不漏错。**

---

## 2. 为什么不用 LangChain / 重量级框架

- 测试流水线是线性流程（读代码 → 生成用例 → 编译运行 → 解析结果 → 修复），大部分步骤不需要 LLM。
- 省 token 的关键是**任务拆分 + 每步小而固定的 prompt + 小模型干便宜活**，与框架无关。
- LangChain 抽象层厚，调试成本高；如确需复杂分支/人工介入节点，再考虑 LangGraph。
- 推荐架构：**裸 Python 主控（libclang + pandas + subprocess）+ LLM API 小调用**。

---

## 3. WinAMS 函数隔离模式下的输入模型

WinAMS 将每个函数隔离、独立运行测试，被测函数的可控输入只有三类：

1. **函数入参**
2. **全局变量**
3. **stub 函数的返回值**（按测试用例逐个设置）

关键推论：条件里用到的变量若来自被 stub 的函数返回值，无需反推约束——直接在 CSV 中给 stub 设返回值即可。WinAMS 把约束求解问题变成了**填表问题**。

---

## 4. 测试用例生成（脚本化核心）

### 4.1 条件拆解

用 libclang 解析判断语句，得到条件表达式语法树。例如：

```c
if ((a > 100) && (b < 5) && flag)
```

拆出 3 个原子条件，每个条件包含：控制变量、比较方向、边界值。

### 4.2 边界值枚举

对每个控制变量生成：

```
{min, min+1, 本身-1, 本身, 本身+1, max-1, max}
```

多输入组合：笛卡尔积，维度过大时用 pairwise 降维。

### 4.3 覆盖率准则组合

- **C0（语句覆盖）**：每条语句至少执行一次
- **C1（分支覆盖）**：每个判断的真/假分支各至少一次
- **MC/DC（修正条件判定覆盖）**：对每个原子条件，生成"仅翻转该条件、其他条件不变"的成对用例（即 T&&T 及三、四条件的组合，有标准组合算法）

脚本按目标准则自动挑选边界值的组合，填入对应的 true/false 分支。

### 4.4 变量来源判定

对每个条件变量判定来源：

- 入参 → 直接设置
- 全局变量 → 直接设置
- 某个 stub 的返回值 → 在 CSV 中逐用例设置

函数被隔离后规模小、来源链短，简单的函数内数据流分析（常量传播）即可覆盖绝大多数情况。**来源判定成功则不调用 LLM**，token 支出完全可控。

---

## 5. LLM 介入的三个环节

### 5.1 来源判定兜底

变量来源绕多层计算、经结构体指针、依赖多处赋值合并时，让 LLM 读该函数（上下文小，token 省）给出映射关系。

### 5.2 有状态 stub

被测逻辑依赖 stub 被调用的**次数或顺序**（如状态机）时，stub 需写成带计数/分支的代码，由 LLM 理解逻辑后生成。

### 5.3 覆盖率闭环

```
跑 WinAMS 批处理
  → 解析未覆盖分支（C0/C1/MC/DC gap）
  → 将未覆盖分支源码片段 + 已有用例喂给 LLM
  → LLM 设计新输入向量
  → 写回测试数据 CSV
  → 再跑
  → 循环到达标或次数上限
```

有覆盖率反馈，生成质量可验证，不易幻觉。MC/DC 条件组合多时一次到位率不高，靠循环兜底。

### 5.4 审查报告起草

对每个未达标项，LLM 结合源码解释"为什么不可达 / 为什么这样设计"，人工只做审核修改。项目制交付中此步最耗人力，自动化收益最大。

---

## 6. 推荐流水线架构

```
┌────────────────────────────────────────────────┐
│              Python 主控（无框架）               │
├────────────────────────────────────────────────┤
│ 1. 扫描模块 → libclang 抽取函数与调用关系        │
│ 2. 生成 stub 骨架 + 编译 ELF（subprocess）       │
│ 3. 拆条件 → 来源判定 → 边界值 + MC/DC 枚举       │
│    └─ 判定失败 → [LLM API] 映射兜底             │
│ 4. 生成 WinAMS 测试数据 CSV                     │
│ 5. WinAMS 批处理执行 → 解析覆盖率                │
│    └─ 未达标 → [LLM API] 覆盖率闭环（≤N 轮）    │
│ 6. 生成测试报告                                  │
│ 7. [LLM API] 起草审查说明 → 人工审核             │
└────────────────────────────────────────────────┘
```

---

## 7. 落地路线

1. **手动走通一个模块**：摸清每步输入输出文件格式（WinAMS 工程文件、测试数据 CSV、覆盖率结果），固化成模板。
2. **脚本化确定性步骤**：stub 骨架、边界值枚举、MC/DC 组合、CSV 生成、报告模板。
3. **接入 LLM 兜底**：来源判定失败分支、覆盖率闭环、审查说明。
4. **批量推广到项目**：主控脚本按模块批量调度。

## 8. 风险与注意

- **MC/DC 用例生成最难**：条件组合多时 LLM 一次到位率不高，依赖覆盖率反馈循环多跑几轮。
- **WinAMS 批处理接口**：不同版本可自动化程度有差异，建议先与 Gaio 确认。
- **审查一致性**：脚本生成的可枚举用例每个项目输出完全一致，这是相对 LLM 全生成的关键优势（审查友好）。
- **Agent 选型不重要**：ZCode / Codex 等能力相近，选有使用规范和审查流程的即可；可在同一模块上对比评测。

## 附：关于测试驱动 agent 的选型问答摘录

- **Q：不以写代码为主、以测试为主，用什么 agent，Codex 吗？**
  A：单元测试 ZCode/Codex/Claude Code 均胜任，关键在测试框架明确 + 在 AGENTS.md 写清"以测试为主，不要大改业务代码"的约束。SIL 仿真环境本身 agent 只能辅助搭建。
- **Q：要做成工作流、省 token，用 Python + LangChain 好吗？**
  A：LangChain 通常过重。省 token 靠任务拆分、小 prompt、小模型，裸 Python 调 API 即可。也可用 agent CLI 的 headless 模式（如 `codex exec`）做批量调度的中间路线。
